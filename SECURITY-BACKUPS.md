# Безопасность и восстановление — 22 октября 2026

## Что работает
- Все публичные API проходят общий серверный контроль: JWT HS256, обязательный срок действия, отсутствие служебного purpose, текущий пользователь и роль из БД. Удалённые аккаунты и старые роли перестают работать сразу.
- Смена пароля отзывает ранее выданные токены. Минимум нового пароля — 10 символов, максимум bcrypt — 72 байта. Слабые старые пароли не менялись автоматически.
- Ограничены попытки входа, регистрации и сброса пароля: 15 на аккаунт и 80 на IP за 15 минут. Выполнение кода — 30/мин, ИИ и действия архива — 10/мин на пользователя. Счётчики PostgreSQL общие для серверных экземпляров.
- Убраны резервные JWT-секреты. Без секрета от 32 символов сервер закрывает доступ. Проверяется сертификат БД.
- Администратор не может удалить свой аккаунт или понизить собственную роль. Отрицательное/дробное начисление монет запрещено.
- Заголовки no-store для API, nosniff, запрет встраивания во фреймы, ограничение referrer и доступа к камере/микрофону/геолокации. CSP пока ограничивает object/base/frame/form, а не все скрипты Expo.

## История тестов
Администратор: «Тарих және көшірмелер» в меню или ссылка в профиле.
Триггеры БД сохраняют состояние перед изменением/удалением теста и вопроса в той же транзакции. Создание/импорт вопросов и ручные копии также записываются. Автор берётся из проверенной сервером сессии, не из тела запроса. Журнал показывает время, действие, автора и количество вопросов/результатов.
Восстановление создаёт НОВЫЙ закрытый тест с новыми ID вопросов. Активные попытки и существующие тесты не перезаписываются. Старые результаты доступны в архиве; они не превращаются в попытки восстановленной копии. История прошлых действий до установки не восстанавливается задним числом.
Журнал нельзя удалить/изменить через API, но владелец базы технически может его изменить. Для защиты от администратора БД нужен отдельный внешний журнал с ограничением записи.

## Полная зашифрованная копия данных
`node server/scripts/backup.cjs create`
Согласованный снимок всех public-таблиц в repeatable-read транзакции, AES-256-GCM; сохраняется в игнорируемую Git папку backups/. Ключ BACKUP_ENCRYPTION_KEY создан локально в .env.local и НЕ включён в файл копии. Сам файл не публикуется через сайт.
Это логический бэкап ДАННЫХ, а не инфраструктуры/схемы. Храните отдельно исходники/миграции, настройки хостинга и изображения из assets. До восстановления подготовьте целевую схему той же версии.

Проверка подлинности:
`node server/scripts/backup.cjs verify backups/FILE.enc.json`
Проверка чтения и загрузки всех значений в изолированные временные таблицы с откатом:
`node server/scripts/backup.cjs verify backups/FILE.enc.json --roundtrip`

Полное восстановление только в ОТДЕЛЬНУЮ пустую БД с применённой схемой/миграциями:
1. Настройте RESTORE_DATABASE_URL локально, не в чате. Он не должен совпадать с DATABASE_URL.
2. Запустите `node server/scripts/backup.cjs restore backups/FILE.enc.json --confirm-empty-target`.
3. Проверьте тесты/учётные записи/результаты в отдельной среде и только затем переключайте приложение.
Скрипт откажется перезаписывать непустые таблицы. Пользовательские триггеры выключаются только в транзакции восстановления, затем возвращаются; внешние ключи остаются активными. Старые сессии и ссылки восстановления пароля аннулируются.

## Развёртывание
Сначала `node server/scripts/migrate-security.cjs`, затем новый сервер/фронтенд. Миграции learning и exams из предыдущих изменений также обязательны. Для начальной версии всех тестов: `npx tsx server/scripts/snapshot-tests.ts`.
Проверки: `node server/scripts/check-security.cjs` и `node server/scripts/check-exams.cjs`. Они создают и удаляют только собственные QA-данные.

## Защита аккаунтов от массового удаления
Миграция server/migrations/20261022-account-protection.sql применена к рабочей БД. users.deleted_at обозначает заблокированный аккаунт. DELETE /api/students/:id требует действующую сессию и текущую роль admin в БД; вместо физического удаления обновляет deleted_at только у student. Свой аккаунт и другие администраторские аккаунты этим запросом заблокировать нельзя. Результаты, назначения вопросов и попытки сохраняются, email остаётся занятым.
Вход, восстановление пароля, auth/me и общий серверный контроль исключают заблокированные аккаунты. Архивирование и восстановление журналируются; старые токены отзываются. Восстановление сейчас выполняется владельцем БД, отдельного публичного API восстановления нет.
Триггер users запрещает обычный физический DELETE независимо от наличия проверки в приложении. Исключение для обслуживания требует явного SET LOCAL app.maintenance_user_purge='on' в транзакции; API этого не делает. Это защита от ошибки приложения, не от владельца БД, который может изменить триггер или выполнить TRUNCATE. Служебные тесты очищают только собственные fixture ID с email @example.invalid внутри отдельной транзакции.
Расширенный check-security проверяет GET/PATCH/DELETE без токена, с испорченным токеном и с ролью student, прямой SQL DELETE, сохранность результата после архивирования и отказ старому токену заблокированного пользователя. Проверки прошли на собственных QA-аккаунтах; реальные аккаунты не удалялись.
